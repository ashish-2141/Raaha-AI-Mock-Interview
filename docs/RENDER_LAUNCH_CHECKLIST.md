# Render launch checklist

This repo includes `render.yaml` for a **free-tier staging deployment** in Render's Singapore region: one Free web service and one Free Key Value instance. This is configured to avoid a fixed service charge. Free services have important limits and are not appropriate for production: the web service sleeps after 15 minutes of inactivity, can restart, and may exhaust included usage; free Key Value has no persistence and its data can disappear on restart. Do not store durable data or conduct a live student pilot on this setup. Review the current free-tier limits and included usage in Render before exposing the app publicly.

The Blueprint sets the Redis service to internal-only access. The web service receives its connection URL through a service reference. It deploys from `main` only when GitHub checks pass and runs `/api/health` as the health check.

## A. Provision the app

1. Sign in to Render with an account authorised to deploy the GitHub repository.
2. In Render, create a new Blueprint and select `ashish-2141/Raaha-AI-Mock-Interview` on `main`.
3. Confirm both resources show the **Free** plan before creating them. Do not upgrade either service or enable paid add-ons.
4. Set these prompted secret values in Render, not GitHub source control:
   - `NEXT_PUBLIC_SUPABASE_URL`
   - `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`
   - `OPENAI_API_KEY`
5. Create the resources and wait for the first deployment to finish.

## B. Validate the live service

1. Open the actual URL generated by Render. Do not assume the URL from the service name.
2. Open `https://<actual-service-host>/api/health`. Expect HTTP 200 and a Redis dependency state of `ok`.
3. Sign in through Supabase. Check that login redirects work with the deployed host.
4. Test resume parsing with a test PDF and confirm the request succeeds.
5. Open `/college-dashboard` while authenticated. Until a TPO mapping is configured, the expected result is a safe HTTP 403, not public access.
6. Inspect logs for startup/configuration failures. Do not paste API keys, cookies, student transcripts or other secrets into logs or reports.

## C. Configure TPO access and pilot enrollment

Do this only after a partner college has approved the pilot and the consent notice is final.

1. In Render's web service environment settings, add `RAAHA_COLLEGE_DASHBOARD_ACCESS_JSON` mapping the TPO's Supabase auth user UUID to the agreed internal college ID.
2. Add `RAAHA_OPERATIONS_ADMIN_USER_IDS` with the UUIDs of authorised operators.
3. Set `RAAHA_PILOT_COLLEGE_ID` to the same college ID.
4. Generate a strong invite code, then set `RAAHA_PILOT_INVITE_CODE`. Share it privately only with approved participants.
5. Add `RAAHA_OPENAI_INPUT_USD_PER_1M` and `RAAHA_OPENAI_OUTPUT_USD_PER_1M` using the approved rates for the model/account, or leave them unset. Costs will remain unknown until rates are supplied.
6. Save the variables and trigger a redeploy. Re-test both authorised and unauthorised accounts.

Render provides variables to Docker builds as build arguments. The public Supabase values are needed during the Next.js build. The OpenAI key is a server secret and should not be declared as a Dockerfile `ARG`.

## D. Run the real load test

From an operator machine, use an authorised TPO browser session. Keep the cookie in a shell environment variable and out of documents.

```sh
RAAHA_LOAD_TEST_BASE_URL=https://<actual-service-host> \
RAAHA_LOAD_TEST_COOKIE='<authorised-tpo-session-cookie>' \
RAAHA_LOAD_TEST_REQUESTS=100 \
RAAHA_LOAD_TEST_CONCURRENCY=10 \
pnpm loadtest:dashboard
```

Save the JSON result, deployed commit SHA, timestamp, selected concurrency, and HTTP status counts. A run against localhost, synthetic data or an unauthenticated URL does not satisfy this gate.

## E. Run and report the 10-student pilot

1. Get written approval from the partner college and final consent/privacy wording.
2. Invite 10 real students using distinct accounts.
3. Ensure each accepts consent before the session starts.
4. Record aggregate completion, response latency, errors, model usage/cost and feedback.
5. Keep candidate IDs and raw answers out of the TPO report.
6. Complete the post-mortem from actual observations. Do not fill gaps with simulated values.
